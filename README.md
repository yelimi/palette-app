# 🎨 Palette App QA

## 1. 프로젝트 개요

**Palette**는 사진을 올리면 대표 색상을 추출하고, 그 색과 어울리는 색상의 옷을 추천해 주는 패션 쇼핑 앱입니다. 어떤 색이 어울리는지 고민하는 사용자가 사진 한 장으로 코디할 상품을 찾을 수 있게 하는 것이 목적입니다.

이 저장소는 Palette 앱(FastAPI 백엔드 + React Native 모바일 앱)을 대상으로 한 **QA 프로젝트**입니다. 요구사항 분석부터 테스트 설계, 자동화, CI 연결까지 진행했습니다.

**핵심 사용자 흐름**

```
회원가입/로그인 → 사진 업로드 → 대표 색상 추출 → 어울리는 색상 상품 추천 → 장바구니 담기
```

**품질상 중점을 둔 부분**

- **인증**: 계정 잠금, 토큰 만료와 로그아웃, 다른 사용자 데이터 접근 차단
- **이미지 업로드**: 사용자가 올리는 파일은 예측할 수 없어서, 포맷·용량·해상도·손상된 파일을 집중적으로 검증
- **기능을 이어서 쓰는 흐름**: 로그인부터 장바구니까지 끊기지 않고 동작하는지

| 항목 | 결과 |
|------|------|
| API 테스트 | **164개** 자동화 (pytest), 전부 통과 |
| 발견 이슈 | **15건** (백엔드 10건: API 테스트 중 발견·수정 / 모바일 5건: 코드 리뷰로 발견, 재현 전) |
| CI | GitHub `main` push 시 Jenkins에서 자동 실행 |

## 2. 테스트 대상과 범위

### 테스트 대상

| 기능 | 설명 | API |
|------|------|-----|
| 회원 인증 | 회원가입, 로그인(JWT), 로그아웃, 비밀번호 변경/재설정. 로그인 3회 실패 시 계정 잠금 | `/auth/*` |
| 색상 추출 / 추천 | 이미지를 올리면 대표 색상을 추출하고, 어울리는 색 5개를 추천 | `POST /colors/extract` |
| 상품 조회 | 성별/카테고리 필터, 색상 기준 정렬, 페이징, 상세 조회 | `GET /products`, `GET /products/{id}` |
| 장바구니 | 상품 담기, 조회, 삭제 | `/cart` |

### 테스트 전략

백엔드 API를 먼저 테스트해서 입력값 검증, 인증, 에러 처리 같은 서버 로직을 확인합니다. 그다음 이 API를 호출하는 모바일 앱 화면을 E2E로 테스트합니다. 화면 테스트에서 실패가 나왔을 때 서버 문제인지 앱 문제인지 빠르게 구분할 수 있도록, 서버를 먼저 검증해 두는 순서입니다.

| 단계 | 테스트 | 목적 | 상태 |
|------|--------|------|------|
| 1 | API 테스트 | 입력값 검증, 인증, 권한, 에러 처리가 API 수준에서 맞는지 확인 | ✅ 완료 |
| 2 | CI 자동화 | 코드가 바뀔 때마다 API 테스트를 자동으로 실행 | ✅ 완료 |
| 3 | 모바일 E2E 테스트 (Appium) | 실제 앱 화면에서 기능이 끝까지 동작하는지 확인 | 🚧 진행 중 |

```
   [ Appium ] ──▶ [ 모바일 앱 (Expo) ]
                         │
                         ▼
   [ Postman / Newman / pytest ] ──▶ [ FastAPI (JWT 인증) ] ──▶ [ PostgreSQL ]

   Jenkins: GitHub main push 때마다 pytest 자동 실행
```

### 테스트 범위

- 기능 테스트 (정상, 예외, 경계값)
- 인증 / 권한 (토큰 상태, 다른 사용자 데이터 접근)
- 입력값 검증 (필수값, 형식, 길이, 공백)
- 파일 업로드 (포맷, 용량, 해상도, 손상된 파일)
- 여러 기능을 이어서 쓰는 사용자 플로우
- API 응답 시간 기준 (기본 500ms, 이미지 업로드 1~5초)

### 도구와 환경

| 구분 | 내용 |
|------|------|
| API 테스트 | Postman (설계, 수동 실행), Newman (CLI 실행), pytest 8.3 (자동화) |
| 모바일 E2E | Appium |
| CI | Jenkins (Docker 컨테이너), GitHub webhook |
| 테스트 DB | PostgreSQL 테스트 전용 DB (`palette_test`), mock 없이 실제 DB 사용 |
| 앱 기술 스택 | FastAPI, SQLAlchemy, PostgreSQL / React Native (Expo) |

## 3. 테스트 설계 방식

API 테스트와 모바일 E2E 테스트 모두 같은 흐름으로 진행합니다.

```
요구사항 분석 → 테스트 케이스 설계 → 수동 실행 → 자동화 → CI 연결
```

### 3.1 API 테스트

```
Postman 수동 실행 → Newman CLI 실행 → pytest 자동화 → Jenkins CI 연결
```

API별로 입력값, 응답, 에러 규칙을 먼저 정리하고, 아래 기법으로 케이스를 뽑았습니다. 케이스 번호(TC)는 테스트 함수 이름과 같아서 바로 코드를 찾을 수 있습니다.

| 기법 | 적용 예시 | 테스트 |
|------|-----------|--------|
| **경계값 분석** | 이름 100자 성공 / 101자 실패, 비밀번호 255자 성공 / 256자 실패 | [TC18~21](tests/api/test_register_scenarios.py) |
| | 이미지 해상도 8000px 성공 / 초과 실패 | [TC105, TC106](tests/api/test_color_scenarios.py) |
| | 페이지 크기(limit) 최솟값 미만, 최댓값 초과 | [TC127~129](tests/api/test_products_scenarios.py) |
| **동등 분할** | 이미지 포맷: 지원(jpg/png/webp/heic) / 미지원(gif → 415) | [TC94~98](tests/api/test_color_scenarios.py) |
| | 잘못된 파일: 빈 파일, 손상된 파일, 확장자만 jpg인 가짜 이미지, 10MB 초과 | [TC100~104](tests/api/test_color_scenarios.py) |
| **상태 전이** | 로그인 2회 실패(401) → 3회째 잠금(423) → 비밀번호 재설정 → 로그인 성공 | [test_account_lock_recovery](tests/api/test_account_lock_recovery.py) |
| **인증 상태 조합** | 보호된 API마다 토큰 없음 / 잘못된 토큰 / 로그아웃된 토큰 3가지를 모두 확인 | [TC144~146](tests/api/test_cart_scenarios.py) 외 |
| **권한** | 다른 사용자의 장바구니 항목 삭제 시도, 사용자별 장바구니 분리 | [TC149, TC156](tests/api/test_cart_scenarios.py) |
| **사용자 시나리오** | 가입 → 로그인 → 이미지 업로드 → 상품 조회 → 장바구니 담기를 한 흐름으로 | [test_user_flow](tests/api/test_user_flow.py) 외 4개 |

## 4. 발견한 이슈와 심각도

### 심각도 판단 기준

| 심각도 | 기준 |
|--------|------|
| 🔴 높음 | 보안, 데이터, 서비스 가용성에 직접 영향 |
| 🟠 중간 | 핵심 기능이 잘못 동작하거나, 사용자가 원인을 알 수 없어 스스로 해결하지 못함 |
| 🟢 낮음 | 우회할 수 있거나 불편한 정도, 데이터 품질에 작은 영향 |

### 백엔드 API (10건, 모두 수정 완료)

API 테스트 케이스를 설계하고 실행하는 과정에서 발견해 수정했습니다.

| # | 심각도 | 이슈 | 판단 근거 |
|---|--------|------|-----------|
| B1 | 🔴 높음 | 이미지 해상도 제한이 없음. 파일 용량이 10MB 이하라도 해상도가 매우 큰 이미지는 처리할 때 메모리를 많이 써서, 한 번의 업로드로 서버 메모리가 부족해질 수 있음 | 서버가 멈추면 모든 사용자가 서비스를 쓸 수 없음 |
| B2 | 🔴 높음 | 회원가입 시 비밀번호 규칙 검사가 없음. 빈 값이나 8자 미만 비밀번호로도 가입됨 | 쉽게 추측할 수 있는 비밀번호로 계정이 만들어짐 |
| B3 | 🔴 높음 | 비밀번호 변경·재설정 시 새 비밀번호에 규칙 검사가 없음. 빈 값이나 8자 미만으로도 바뀜 | 가입 때는 규칙을 지켜도, 변경으로 약한 비밀번호를 만들 수 있음 |
| B4 | 🟠 중간 | 파일 앞부분은 정상이지만 중간 데이터가 잘린 이미지(전송이 끊긴 파일 등)를 올리면 500 서버 에러 발생 | "잘못된 이미지"라는 안내 대신 서버 에러만 보여서, 사용자는 무엇이 문제인지 알 수 없음 |
| B5 | 🟠 중간 | 이메일 대소문자를 서로 다른 값으로 취급함. `Hong@test.com`과 `hong@test.com`으로 각각 가입되고, 가입 때와 다른 대소문자로 로그인하면 실패 | 한 사람이 계정을 여러 개 만들 수 있고, 정상 사용자가 로그인에 실패함 |
| B6 | 🟠 중간 | 회원가입 시 이름 검사가 없음. 빈 값, 100자 초과, 특수문자·숫자가 들어간 이름도 저장됨 | 의미 없는 이름이 저장되어 화면에 그대로 표시됨 |
| B7 | 🟢 낮음 | 이메일 앞부분(@ 앞)에 한글이 들어가도 가입되고, 길이 제한도 없음 (이메일 표준: @ 앞 64자, 전체 254자) | 표준에 맞지 않는 이메일이지만, 실제 사용자가 입력하는 경우는 드묾 |
| B8 | 🟢 낮음 | 이름 앞뒤 공백이 그대로 저장되고, 비밀번호 앞뒤 공백도 허용됨 | `"홍길동 "`처럼 저장되어 같은 이름이 다른 값으로 취급됨. 실수로 들어간 비밀번호 공백은 사용자가 알아채기 어려움 |
| B9 | 🟢 낮음 | 로그인 시 이메일·비밀번호 길이 제한이 없음 | 너무 긴 값으로는 애초에 가입할 수 없어서 로그인이 실패할 뿐, 사용자 영향은 작음 |
| B10 | 🟢 낮음 | 현재 비밀번호와 같은 값으로 변경해도 성공함 | 비밀번호 유출이 의심될 때 바꾸는 의미가 없어짐. 다만 사용자가 일부러 하는 경우라 영향은 작음 |

### 모바일 앱 (5건, 코드 리뷰로 발견)

Appium 테스트 케이스를 설계하면서 앱 코드를 검토해 발견했습니다. **아직 앱을 실행해 재현하지 않았고, 수정도 하지 않았습니다.** Appium 테스트로 재현한 뒤 수정할 예정입니다.

| # | 심각도 | 이슈 | 판단 근거 |
|---|--------|------|-----------|
| M1 | 🔴 높음 | 로그아웃할 때 앱에 저장된 토큰만 지우고, 서버 로그아웃 API(`/auth/logout`)는 호출하지 않음. 그래서 서버에서는 그 토큰이 계속 유효함 | 토큰이 다른 곳에 복사되어 있었다면, 로그아웃한 뒤에도 그 토큰으로 계정 정보와 장바구니에 계속 접근할 수 있음 |
| M2 | 🟠 중간 | 잘못된 비밀번호나 가입하지 않은 이메일로 로그인하면, 오류 안내 없이 화면에 아무 변화가 없음 | 로그인은 모든 사용자가 거치는 기능인데, 사용자는 실패했는지조차 알 수 없음 |
| M3 | 🟠 중간 | 이미지를 분석하는 동안에도 사진 선택 버튼을 다시 누를 수 있음. 이미지를 연달아 고르면 먼저 보낸 요청의 응답이 나중에 도착해, 화면에는 새 이미지가 보이는데 추천 결과는 이전 이미지 것이 표시될 수 있음 | 사용자가 고른 사진과 맞지 않는 추천 결과를 보여 줌 |
| M4 | 🟢 낮음 | 상품 상세 정보를 불러오지 못하면 오류 알림을 닫은 뒤 빈 화면만 남고, 다시 불러오는 버튼이 없음 | 하단 탭으로 홈에 돌아가 다른 상품을 볼 수 있어 우회할 수 있음 |
| M5 | 🟢 낮음 | 상품 상세 화면 상단에 뒤로가기 버튼이 없음 | 하단 탭을 눌러 홈으로 돌아갈 수 있어 우회할 수 있음 |

### 개선점

앞으로 진행할 테스트입니다.

- **모바일 E2E 테스트 CI 연결**: API 테스트처럼 Jenkins에서 자동으로 실행되게 합니다.
- **웹 테스트**: 앱이 Expo 기반이라 같은 코드로 웹에서도 실행됩니다. 브라우저에서 핵심 사용자 흐름(로그인 → 사진 업로드 → 색상 추천 → 장바구니)을 E2E로 자동화하고, 브라우저별 동작 차이와 화면 크기에 따른 레이아웃을 확인합니다.
- **성능, 부하 테스트**: 지금은 기능 테스트 안에서 API 응답 시간 기준만 확인합니다. 여러 사용자가 동시에 요청할 때의 응답 시간과 에러율을 확인합니다.
- **보안 테스트**: 지금은 인증과 권한 확인까지만 포함합니다. 토큰 변조, 입력값을 이용한 공격(SQL 인젝션 등)에 대한 테스트로 넓힙니다.
- **주문, 결제 테스트**: 지금 앱은 장바구니 담기까지만 구현되어 있어서, 쇼핑 흐름의 마지막 단계인 주문과 결제는 검증하지 못했습니다. 결제는 돈과 직결되어 오류가 생기면 영향이 가장 큰 영역이므로, 기능이 추가되면 우선 검증할 대상입니다. 결제 실패 처리, 중복 결제 방지, 주문 후 장바구니 상태 등을 확인합니다.
